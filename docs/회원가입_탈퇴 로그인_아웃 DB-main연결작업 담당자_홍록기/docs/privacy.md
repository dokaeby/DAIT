# 개인정보 처리 문서 (회원 파트)

AGENTS.md 5-5의 1번("수집하는 개인정보는 필요한 최소한으로 한다. 목적, 보관 기간, 삭제 절차를 문서화한다")과
기획서 결정 대기 P0 "개인정보 보관 기간과 탈퇴 삭제 방식"에 따른 문서다. 법적 검토를 거친 문서가 아니라
개발 기준 문서이며, 실제 서비스로 운영하기 전에는 담당자 검토가 필요하다.

## 1. 수집 항목과 목적

| 항목 | 저장 위치 | 목적 | 비고 |
|---|---|---|---|
| 이메일 | `users.email` | 계정 식별, 로그인 | 소문자로 통일해 저장 |
| 비밀번호 | `users.password_hash` | 로그인 확인 | argon2id 해시만 저장. 평문은 저장하지 않는다 |
| refresh 토큰 | `refresh_tokens.token_hash` | 로그인 유지 | SHA-256 해시만 저장. 원문은 서버에 없다 |
| 관심사 | `user_interests` | 관심 분야 맞춤 표시 | 고정 목록의 코드만 저장 |
| 가입 시각 | `users.created_at` | 계정 관리 | UTC |
| 접속 IP, 사용자 id, 시각 | 감사 로그 | 보안 이벤트 추적 | 가입·로그인·갱신·로그아웃·탈퇴 기록. 이메일·비밀번호·토큰은 기록하지 않는다 |

수집하지 않는 것: 이름, 전화번호, 주소, 결제 정보, 위치 정보. LLM·외부 API에는 사용자 정보를 보내지 않는다.

## 2. 보관 기간

| 대상 | 보관 기간 | 근거 |
|---|---|---|
| 계정 정보(이메일, 비밀번호 해시, 관심사) | 계정이 존재하는 동안. 탈퇴하면 즉시 삭제 | 이용 목적이 끝나면 지체 없이 파기 |
| refresh 토큰 해시 | 발급 후 14일(`REFRESH_TOKEN_DAYS`) 또는 로그아웃·탈퇴 시. 만료된 행의 정기 삭제 작업은 후속 과제 | 로그인 유지 목적 |
| 감사 로그 | **90일** 후 삭제 | 보안 사고 조사 목적. 서비스를 실제로 운영하게 되면 1년 이상으로 늘리는 것을 검토한다 |
| DB 백업 파일 | 14일 | `backup_restore.md`. 백업에는 탈퇴 전 데이터가 남을 수 있어 보관 기간을 짧게 둔다 |

감사 로그의 90일 삭제는 로그를 수집·보관하는 운영 설정(파일 회전, 수집 도구)에서 적용한다. 앱 코드는 로그를
표준 에러로만 내보내며 보관 기간을 직접 관리하지 않는다.

## 3. 삭제 절차 (회원탈퇴)

1. 사용자가 로그인한 상태에서 `DELETE /v1/me`에 비밀번호를 다시 보낸다(본인 재확인).
2. 비밀번호가 맞으면 `users` 행을 삭제한다. 외래키 `ON DELETE CASCADE`로 `refresh_tokens`, `user_interests`가
   함께 삭제된다. 비식별화가 아니라 행 삭제다.
3. 탈퇴 직후 남은 access 토큰은 요청마다 DB에서 사용자를 다시 확인하므로 즉시 거부된다.
4. 같은 이메일로 다시 가입할 수 있고, 이전 관심사는 복구되지 않는다.
5. 감사 로그에는 탈퇴 사실(`withdraw success`, 사용자 id, 시각, IP)이 위 보관 기간 동안 남는다.
6. 백업 파일에는 탈퇴 전 데이터가 남아 있을 수 있다. 백업에서 복구했다면 탈퇴 처리된 사용자를 다시 삭제한다
   (`backup_restore.md`의 복구 후 확인 5번).

## 4. 사용자에게 안내할 내용 (화면 담당 참고)

가입 화면에 아래 요지를 보여 준다: 수집하는 항목(이메일, 비밀번호는 암호화 저장, 선택한 관심사), 이용 목적, 보관
기간(탈퇴 시 즉시 삭제, 보안 기록은 90일), 탈퇴 방법. 문구의 최종 확정은 기획서 담당자가 한다.

## 5. 미결·후속

- 감사 로그 보관 기간 90일은 개발 기준 제안값이다. 팀이 다른 기간을 정하면 이 문서를 고친다.
- 만료된 refresh 토큰을 주기적으로 지우는 정리 작업은 아직 없다(후속).
- 운영 DB를 PostgreSQL(Supabase)로 옮기면 삭제·백업 절차를 그쪽 도구에 맞춰 다시 쓴다.
