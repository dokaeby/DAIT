# 회원 파트 결정 기록

되돌리기 어려운 결정만 한 줄 이유와 함께 적는다. (AGENTS.md 9절 6번)

## 2026-11-07: 설정은 pydantic-settings, 알 수 없는 환경변수는 무시

- 결정: `Settings`는 `extra="ignore"`로 읽는다. (모델은 `extra="forbid"`가 기본이나 설정 클래스만 예외)
- 이유: 팀 공용 `.env`에 다른 파트 키(REDIS_URL 등)가 섞여도 회원 파트 시작이 막히지 않게 한다. 값이 잘못된 경우는 그대로 시작을 거부한다.

## 2026-11-07: APP_ENV는 debug|release 두 값만

- 결정: `test` 모드를 추가하지 않고 테스트는 `debug`로 돌리며 DB 위치만 환경변수로 바꾼다.
- 이유: AGENTS.md 2절. 09 절차서의 `APP_ENV=test`와 다르지만 코드 설계 기준이 우선이다.

## 2026-11-07: 의존성 lock은 uv

- 결정: `uv.lock`으로 버전을 고정하고 `pyproject.toml`에 정확한 버전(==)을 적는다.
- 이유: AGENTS.md "lock 파일(uv 또는 pip-tools)". 한 도구로 가상환경·설치·lock이 끝난다.

## 2026-11-07: sqlite 외래키 PRAGMA는 연결마다 켠다

- 결정: `repositories/db.connect`가 매 연결에서 `PRAGMA foreign_keys = ON`을 실행한다.
- 이유: sqlite 기본값이 꺼짐이라 탈퇴 시 `ON DELETE CASCADE`가 동작하지 않는다.

## 2026-11-07: 본문 크기 제한은 Content-Length 기준

- 결정: 미들웨어에서 Content-Length가 1MiB를 넘으면 413으로 거부한다.
- 이유: 가장 단순한 1차 방어. 청크 전송은 이후 입력 모델의 길이 제한(`max_length`)이 막는다.

## 2026-11-07: 테스트 클라이언트는 httpx 0.28.1 유지

- 결정: httpx2로 바꾸지 않는다. (사용자 결정 2026-11-08 "문제 없으면 그대로 진행")
- 이유: starlette TestClient는 httpx2가 없으면 httpx로 대신 동작하고 deprecation 경고만 낸다. 테스트 전용이며 동작·보안 문제는 확인되지 않았다.
- 영향: pytest에 경고 1건이 남는다. starlette가 httpx 지원을 끊으면 그때 교체한다.

## 2026-11-08: 로그인 유지는 AGENTS.md 기준 (access 15분 + 회전 refresh 14일)

- 결정: 사용자가 한때 제안한 "2시간 미사용 시 로그아웃"과 서버 세션 방식은 취하하고, 기준 문서대로 간다.
- 이유: AGENTS.md 5-1의 2번(짧은 access + 회전 refresh)과 08 UT-AUTH-006·008·009가 기준이다.
- 영향: 화면은 401을 받으면 refresh로 조용히 갱신해야 한다(프런트 요청, README 10절).

## 2026-11-08: 중복 이메일 가입은 이메일을 언급하지 않는 409로 거절

- 결정: 중복이면 `SIGNUP_FAILED`(409) "가입을 완료할 수 없습니다"만 낸다. 해시를 먼저 계산해 시간 차이를 줄인다.
- 이유: 이메일 인증이 없고 가입 즉시 로그인되는 구조라 AGENTS.md 5-1의 4번(가입 응답 동일)을 완전히 지킬 수 없다.
- 한계: 409 여부로 가입자인지 약하게 알 수 있다. 2단계 이메일 인증 때 응답을 통일해 해소한다.

## 2026-11-11: 중복 이메일은 "이미 가입된 이메일입니다."로 알린다 (계정 열거 방지 예외)

- 결정: 위 2026-11-08 결정을 바꿔, 중복 가입은 409 `SIGNUP_FAILED`에 "이미 가입된 이메일입니다."를 낸다. 사용자 결정.
- 이유: 가입 실패 이유가 화면에 보이지 않아 사용자가 무엇을 고쳐야 할지 몰랐다.
- 예외 명시: AGENTS.md 5절 "계정 열거 방지"의 예외다. 다른 곳(로그인 401, 토큰 401)은 그대로 이유를 구분하지 않는다.
- 완화: 가입 요청 자체의 시도 제한(429)은 아직 없다. 로그인 잠금(429)만 있으므로 가입 시도 제한은 2단계 제안으로 남긴다.
- 되돌리는 법: `core/errors.py`의 `SignupFailedError.message`를 일반 문구로 되돌린다.

## 2026-11-08: 유출 비밀번호 차단은 로컬 목록만

- 결정: 흔한 비밀번호 약 75개와 이메일 앞부분 포함 금지만 막는다(가입 시에만).
- 이유: 외부 유출 목록 조회는 네트워크 호출이 필요해 단위 테스트 원칙(네트워크 0)과 장애 격리에 부담이 크다.
- 한계: 목록에 없는 유출 비밀번호는 통과한다. 2단계에서 외부 조회를 붙인다.

## 2026-11-08: 로그인 잠금은 메모리 구현

- 결정: 계정 5회·IP 20회 실패부터 60초, 두 배씩 최대 15분 잠근다. `Throttle` Protocol 뒤에 두어 Redis로 교체한다.
- 이유: Redis를 아직 쓰지 않기로 했다(README 4절 c).
- 한계: 서버를 다시 시작하거나 서버가 여러 대면 기록이 공유되지 않는다. IP는 접속 소켓 주소만 쓴다(프록시 헤더는 위조 가능).

## 2026-11-08: 마이그레이션은 SQLAlchemy 기본 타입 + 시각은 ISO 문자열 삽입

- 결정: 시각 컬럼은 `DateTime(timezone=True)`로 만들고 sqlite 저장소는 UTC ISO 문자열로 넣는다.
- 이유: SQLite·PostgreSQL 공통 문법만 쓰는 규칙(README 5.4). PostgreSQL 연동 때 repository의 연결 부분만 교체한다.

## 2026-11-08: 로그아웃 뒤에도 이미 발급된 access 토큰은 만료까지 유효

- 결정: 로그아웃은 refresh 토큰만 전부 폐기하고 access JWT는 차단 목록을 두지 않는다.
- 이유: 즉시 차단하려면 토큰 차단 목록(Redis 또는 메모리)이 필요하다. AGENTS.md 5-1의 2번도 refresh 무효화를 요구한다.
- 한계: 최대 `ACCESS_TOKEN_MINUTES`(15분) 동안 훔친 access 토큰이 쓰일 수 있다. 탈퇴·정지 사용자는 요청마다 DB에서 확인하므로 즉시 막힌다.

## 2026-11-08: 폐기된 refresh 토큰은 이유와 관계없이 "재사용"으로 보고 family 전체를 폐기

- 결정: 이미 폐기된 토큰 제시, 동시에 같은 토큰으로 두 번 요청한 경우, 로그아웃 뒤 옛 토큰 제시를 모두 같은 처리로 본다.
- 이유: 구분하려면 폐기 사유 컬럼이 필요하고, 어느 경우든 그 토큰은 더 이상 믿을 수 없다. 단순함과 보수적 보안을 택했다.
- 영향: 감사 로그의 `refresh reuse_detected`가 로그아웃 뒤 정상 사용자의 낡은 토큰 제시에도 찍힐 수 있다(경보 기준을 정할 때 고려).

## 2026-11-08: 탈퇴는 DELETE /v1/me + 본문 비밀번호, 실패는 로그인 잠금과 같은 횟수에 합산

- 결정: 계정 5회·IP 20회 기준을 로그인과 공유한다. 성공/로그아웃·탈퇴 응답은 204 대신 200 `{"result":"done"}`.
- 이유: response_model 필수 원칙(AGENTS.md 1절)을 지키고, 훔친 access 토큰으로 비밀번호를 무차별 대입하는 길을 막는다.
- 주의: 일부 HTTP 클라이언트는 DELETE 본문을 지우므로 프런트가 본문 전송을 확인해야 한다(README 10절).

## 2026-11-08: 로그인된 요청의 가입·로그인은 409 ALREADY_LOGGED_IN

- 결정: 유효한 Bearer 토큰이 있으면 거절한다. 만료·잘못된 토큰은 로그아웃 상태로 보고 정상 처리한다.
- 이유: README 4절 d(로그인 상태별 노출 규칙의 서버 쪽 지원).

## 2026-11-08: 관심사는 별도 리비전(0002)과 별도 파일로 분리

- 결정: `user_interests`는 `users`를 모르고 `user_interests.user_id -> users.id`(CASCADE) 한 방향만 둔다. 라우터는 main에서 한 줄이다.
- 이유: README 5절. 로드맵상 MVP 화면에서 관심 메뉴가 빠질 수 있어도 가입·로그인·탈퇴가 똑같이 동작해야 한다.
- 영향: 0002만 되돌리면 관심사만 사라진다(테스트로 확인). 단, 가입 요청의 `interests` 필드와 `auth_service.signup`의 저장 호출은 관심사를 뺄 때 함께 지워야 한다.

## 2026-11-08: 관심사 코드 검증은 Pydantic Enum, DB에는 CHECK를 두지 않음

- 결정: DB 컬럼은 문자열이고 코드 목록 검증은 요청 모델(Enum)이 한다.
- 이유: README 5.4(PostgreSQL 전용 타입 금지, 값 검증은 Pydantic). 코드 목록을 바꿀 때 마이그레이션 없이 Enum만 고치면 된다.
- 한계: DB에 직접 쓰는 다른 코드가 잘못된 값을 넣어도 막지 못한다. 읽을 때는 카탈로그에 없는 값을 무시한다.

## 2026-11-08: 카탈로그 API는 공개

- 결정: `GET /v1/interests/catalog`는 로그인 없이 호출할 수 있다.
- 이유: 가입 화면에서 로그인 전에 보여 줘야 한다. 고정 목록이라 개인 정보가 없다.

## 2026-11-08: 로그인·가입·세션 응답에 관심사를 붙이는 일은 api 계층에서 한다

- 결정: `api/auth.py`의 `_attach_interests`와 `api/me.py`의 session이 `interest_service.list_interests`를 불러 응답의 `interests`에 채운다. `auth_service`는 관심사를 모른다.
- 이유: 로그인 직후 메인 화면이 관심사를 바로 받게 하면서도(사용자 요구) 인증 서비스와 관심사의 결합을 피한다(README 5절).
- 영향: 관심사를 뺄 때는 `_attach_interests`와 호출 두 곳, session의 붙이는 3줄, 응답 모델의 `interests` 필드를 지운다.
- 저장소: 관심사는 `DATABASE_URL`이 가리키는 로컬 PC의 sqlite 파일(`user_interests`)에 있다. 기본 경로는 실행 폴더의 `dait.db`이므로 `.env`에 절대 경로를 적어 두는 것을 권장한다.

- 2026-11-09 사용자 승인: 관심사는 AGENTS.md "개인화=2단계"의 예외로 1단계에 포함하고, 기획서 문서 일괄 갱신 규칙은 회원 파트에 적용하지 않고 README 기능별 기록(11·12절)으로 대체한다.

## 2026-11-11: 이메일 2차 인증은 로그인 단계만, 기본 꺼짐

- 결정: `TWO_FACTOR_ENABLED=true`일 때만, 비밀번호가 맞은 로그인에 6자리 코드를 메일로 보내 확인한 뒤 토큰을 준다. 기본은 꺼짐이고 꺼져 있으면 로그인·경로가 예전과 같다(2차 인증 경로 자체가 등록되지 않는다). 가입 이메일 인증은 이번 범위에서 제외한다. 사용자 승인(매뉴얼 34번 "로그인 2차 인증만").
- 코드 저장: 코드 원문은 저장하지 않고 `HMAC-SHA256(OTP_HASH_SECRET, 챌린지키:코드)`만 sqlite `two_factor_challenges`에 둔다. 6자리는 일반 해시면 즉시 역산되므로 서버 비밀 키를 섞었다. 챌린지 번호(`challenge_id`)도 SHA-256만 저장한다.
- 저장소: `CodeStore` 인터페이스 뒤에 sqlite 구현을 두었다. Redis(TTL)로 바꿀 때 구현만 바꾼다(README 4절 c).
- 규칙: 유효 5분, 코드당 5회 시도(마지막 실패 때 폐기), 재발송 60초 간격·최대 5번(재발송하면 시도 0으로), 사용자당 챌린지 하나, 성공 시 삭제, `compare_digest`, 실패는 모두 같은 401 `INVALID_TWO_FACTOR`.
- 메일: `smtplib` + STARTTLS, 10초 타임아웃, 응답을 보낸 뒤 백그라운드로 발송. 실패해도 로그인 응답은 나가고 재발송으로 복구한다.
- 한계: 로그인 잠금과 같이 시도 제한 중 일부는 sqlite에 있어 서버가 여러 대여도 공유된다. 메일 지연이 길면 사용자는 재발송 60초를 기다려야 한다. 2차 인증이 켜진 계정의 로그인 응답은 비밀번호가 맞고 틀림에 따라 달라진다(비밀번호를 알아야 계정 존재 여부가 드러난다).
- 되돌리는 법: `TWO_FACTOR_ENABLED=false`. 테이블까지 지우려면 `alembic downgrade 0002_interests`.
