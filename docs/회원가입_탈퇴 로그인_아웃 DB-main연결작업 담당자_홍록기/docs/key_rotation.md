# 서명 키(JWT_SECRET) 교체 절차

access 토큰은 `JWT_SECRET`으로 서명한다. refresh 토큰은 서명이 아니라 무작위 문자열(DB에는 해시만 저장)이라
키를 바꿔도 refresh 토큰은 그대로 유효하다.

## 정기 교체 또는 유출이 의심될 때

1. 새 키를 만든다: `python -c "import secrets; print(secrets.token_urlsafe(48))"` (32자 이상).
2. 배포 환경의 `JWT_SECRET`을 새 값으로 바꾸고 서버를 다시 시작한다. 코드·Git·이미지·로그에는 넣지 않는다.
3. 영향: 기존 access 토큰(최대 `ACCESS_TOKEN_MINUTES`분)은 즉시 무효가 된다. 사용자는 refresh 토큰으로
   새 access 토큰을 받는다(refresh 기능은 모듈 3에서 구현. 그 전에는 다시 로그인).
4. 유출이 확정이면 추가로 `refresh_tokens` 테이블을 비워 모든 사용자를 다시 로그인시킨다.
   (모듈 3의 "전체 무효화" 기능이 생기면 그 기능을 쓴다.)
5. 이전 키는 폐기하고 교체 시각을 팀 채널에 남긴다.

## OTP_HASH_SECRET (2차 인증 코드 해시 키) 교체

2차 인증 코드는 `OTP_HASH_SECRET`을 섞은 해시로만 저장한다. 코드는 5분만 유효해서 키를 바꿔도 잃는 것은 진행 중인 챌린지뿐이다.

1. 새 키를 만든다: `python -c "import secrets; print(secrets.token_urlsafe(48))"` (32자 이상).
2. 배포 환경의 `OTP_HASH_SECRET`을 바꾸고 서버를 다시 시작한다.
3. 영향: 그 순간 코드 입력 중이던 사용자는 코드가 맞지 않게 되어 다시 로그인해야 한다. 정리가 필요하면 `two_factor_challenges` 테이블을 비워도 된다(로그인 상태에는 영향 없음).

## SMTP_APP_PASSWORD (구글 앱 비밀번호) 교체

1. 구글 계정의 앱 비밀번호 화면에서 기존 앱 비밀번호를 삭제(폐기)하고 새로 만든다. 계정 자체의 비밀번호와는 다르다.
2. 배포 환경의 `SMTP_APP_PASSWORD`를 새 값으로 바꾸고 서버를 다시 시작한다. 코드·Git·이미지·로그·채팅에는 넣지 않는다.
3. 유출이 의심되면 먼저 1번(폐기)부터 한다. 폐기 즉시 메일 발송이 실패하지만 로그인 응답은 정상이고 사용자는 재발송을 누를 수 있다.
4. 교체 시각을 팀 채널에 남긴다.

## 한계

키를 두 개 동시에 허용하는 무중단 교체는 지원하지 않는다. 필요해지면 그때 추가한다.
