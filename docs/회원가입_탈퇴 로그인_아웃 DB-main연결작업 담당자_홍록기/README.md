# 역할과 범위
- 너는 팀프로젝트 "다잇(DAIT)" 뉴스 큐레이터 서비스에서 **회원 파트**만 맡는다.
- 만들 것: 가입·탈퇴, 로그인·로그아웃, refresh 토큰, 관심사 선택·저장·조회·수정, sqlite3 로컬 저장, 최소 main(합칠 때 라우터 등록 한 줄만 옮김).
- **API(기능 코드)만** 만든다. 화면 코드는 만들지 않는다.
- 기사 수집·요약·번역·목록·랭킹·정렬 등 다른 파트는 만들지 않는다. 맞닿는 지점은 인터페이스만 정하고 먼저 보고한다.

# 기준 문서 (이 순서로 따른다)
1. `AGENTS.md`와 `CLAUDE.md`: 코드 설계 기준이며 충돌 시 **최우선**.
2. `main1.py`: **주석 형식만** 따른다(AGENTS.md 9절의 "간결"보다 우선). 그 안의 기술(Streamlit 등)은 쓰지 않는다.
   - 모듈 docstring 한 줄(역할과 하지 않는 일), 함수 docstring은 요약 한 줄 + 빈 줄 + `입력:` / `출력:` / `기능:` 3항목.
   - 인라인 주석은 "왜/주의점" 위주, 함수 사이 빈 줄 2줄, 예외 메시지는 한국어.
3. `08_단위_test_cases_v1.0.1.md`, `09_단위_test_procedure_v1.0.1.md`: 구현 **후 자체 테스트** 기준.

# 확정된 결정
- 관심사: 대주제 3개(ai, economy, society) x 소주제 5개 = 15개. 저장은 영문 고정 코드(예: `ai.agents`), 상한 15, 건너뛰기=빈 목록, 가입 후 조회·수정 가능. 조회 응답은 `code`·`name`(한글)·`group`을 함께 주고, 이용자 화면에는 한글 이름만 보인다. 기사 쪽 카테고리 Enum은 건드리지 않는다. 임시 기능 ID는 `FR-INTEREST-01`.
- 합치기 안전 방식: 관심사는 독립 모듈(라우터·서비스·저장소·마이그레이션 분리). users 테이블은 관심사에 의존하지 않는다. 가입 요청의 관심사 필드는 선택(기본 빈 목록). 마이그레이션은 SQLite·PostgreSQL 공통 문법만 쓰고 downgrade를 작성한다.
- 저장소: Redis는 추후 도입. 지금은 sqlite3 로컬 저장, 로그인 잠금은 인터페이스 뒤 메모리 구현. sqlite는 `PRAGMA foreign_keys=ON`.
- 인증: argon2id, Bearer 토큰, 짧은 access + 회전 refresh(family), 로그아웃·탈퇴 시 refresh 전부 무효화, 탈퇴는 비밀번호 재확인 후 실제 삭제. 가입은 `password_confirm`·`terms_accepted` 필수, 이메일 소문자 저장, 비밀번호 최대 128자, users에 `role`·`status`. 로그인 실패 응답은 이메일 없음/비밀번호 틀림이 동일(계정 열거 방지). 감사 로그에 비밀번호·토큰은 넣지 않는다.
- 로그인 상태별: `GET /v1/me/session`으로 상태 확인, 상태에 맞지 않는 요청(로그인 상태의 가입·로그인, 로그아웃 상태의 로그아웃·탈퇴)은 409/401로 거부.
- `APP_ENV`는 debug|release만 허용(09의 `APP_ENV=test`는 따르지 않고 테스트는 debug로 실행).
- 모든 경로는 `/v1` 접두사, 에러 형식은 `{code, message, request_id}`.
- 승인된 새 라이브러리: argon2-cffi, PyJWT, email-validator, alembic, uvicorn, ruff, pyright, pytest, pytest-asyncio, httpx, pytest-cov. 그 밖의 것은 승인 후 추가.

# 작업 순서
1. 모듈 하나씩 구현한다. 한 번에 수정하는 파일은 최소로 한다.
2. 인증·세션·비밀값 처리 코드는 변경 **전에** 계획을 보여주고 승인을 받는다(plan 모드, 승인 전 파일 수정 금지).
3. 구현 후 `ruff check .`, `ruff format --check .`, `pyright`, `pytest tests/unit -q`를 **직접 실행**하고 실제 출력으로 보고한다. 실행하지 못했으면 못 했다고 쓴다. 설정 완화·`type: ignore`·`Any` 금지.
4. 08·09 기준으로 자체 테스트를 하고, 실제로 실행한 경우에만 이렇게 쓴다: "해당 기능은 08 단위 test cases 파일과 09 단위 test procedure 파일을 기준으로 테스트가 완료되었습니다." 실제 명령 출력과 통과/실패 수를 함께 적는다. 하지 않았으면 이 문장을 쓰지 않는다.
5. 악의적 입력, 외부 실패, 중복 실행을 점검해 1~2줄로 보고한다.
6. 끝나면 변경한 파일 목록과 이유를 요약한다.

### 2.2 우선순위 규칙

1. **주석 형식은 main1.py가 AGENTS.md보다 우선한다.** (사용자 확정 2026-11-07)
2. 주석 외의 규칙이 서로 충돌하면 **임의로 정하지 않는다.** 충돌 지점과 대안을 먼저 사용자에게 보고하고 승인을 기다린다.
3. **구현 기준은 AGENTS.md와 CLAUDE.md("지정 파일 2개"), 테스트 기준은 08·09 문서다.** AGENTS.md·CLAUDE.md는 코드 설계 기준이며 충돌 시 **최우선**이다. `08_단위_test_cases_v1.0.1.md`와 `09_단위_test_procedure_v1.0.1.md`는 구현 후 자체 테스트 기준이다. 08·09가 요구하는 항목이 AGENTS.md와 충돌하지 않고 설계에 없으면 설계에 **추가**한다. 충돌하면 AGENTS.md대로 구현하고, 테스트와 어긋나는 점은 사용자에게 **보고**한다 (8절 14·16번). 새 항목(라이브러리, 컬럼, 환경변수 등)이 필요하면 필요한 내용을 요청하고 승인을 기다린다 (4절 k).
4. 기획서(문서 세트)는 이 파트에서 **직접 수정하지 않는다.** 바뀐 점은 10절 "문서 담당자 반영 요청"에 적어 문서 담당자가 반영하게 한다.

### 2.3 주석 형식 (main1.py 기준)

| 항목 | 규칙 |
|---|---|
| 모듈 docstring | 한 줄. 파일의 역할과 하지 않는 일을 적는다. |
| 함수 docstring | 첫 줄 한 줄 요약 → 빈 줄 → `입력:` / `출력:` / `기능:` 3항목 고정. 인자는 `이름 (설명)`, 출력은 형태·형식 명시, 기능에는 예외 조건과 제한값(timeout 등)을 적는다. 인자가 없으면 `입력: 없음(출처 설명)`. 작은 함수에도 똑같이 적용. |
| 문체 | 한국어 평서형("~한다", "~함", 명사형 종결 혼용). 전문용어는 괄호로 풀이. |
| 인라인 주석 | 코드 뒤 두 칸 띄우고 `#`. "무엇"이 아니라 "왜/주의점" 위주. 자명한 줄에는 달지 않는다. |
| 코드 형태 | 함수 사이 빈 줄 2줄. 예외 메시지는 한국어. 사용자에게 보이는 오류는 일반 메시지. |

### 2.4 코드 작업 규칙 (CLAUDE.md)

CLAUDE.md는 AGENTS.md의 모든 절대원칙에 더해 아래를 요구한다. 회원 파트의 모든 코드 작업에 적용한다.

1. 설계 요약 단계는 **plan 모드**로 하고, 승인 전에는 파일을 수정하지 않는다.
2. 코드 수정 후 `ruff check`, `ruff format --check`, `pyright`, `pytest`를 직접 실행하고 **실제 출력**을 근거로 보고한다. 실행하지 못했으면 못 했다고 적는다.
3. **인증, 세션, 크롤러 SSRF 방어, 비밀값 처리 코드를 바꿀 때는 변경 전에 계획을 보여주고 승인**을 받는다. 회원 파트의 가입·로그인·로그아웃·탈퇴·refresh 코드는 모두 여기에 해당한다.
4. 실행 금지 명령: `git push`, `git reset --hard`, `git clean -f`, `git branch -D`, `rm -rf`, `sudo`, `curl ... | sh`. 필요하면 제안만 하고 사용자가 직접 실행한다.
5. `.env`, 키 파일, 인증서 등 비밀값 파일은 읽거나 출력하지 않는다. 필요한 환경변수 **이름만** `.env.example`에 추가한다.
6. 한 번에 수정하는 파일은 최소한으로 하고, 마지막에 변경한 파일 목록과 이유를 요약한다.

## 5. 합치기 안전 방식

파트 담당자들이 각자 만든 코드를 합칠 때 에러나 충돌이 나지 않게 지키는 규칙이다. 특히 관심사 기능은 로드맵 원칙 6("현재 단계에 없는 기능은 테이블·추상화를 미리 만들지 않는다")과 부딪히므로, **나중에 빼거나 미뤄도 다른 기능이 깨지지 않게** 만든다.

### 5.1 왜 필요한가

- 관심사는 기획서상 단계 2(개인화)인데 1단계에서 만든다 (4절 g).
- 로드맵 4.3절은 MVP 화면에서 "관심" 메뉴를 빼기로 되어 있었으나, 관심사 기능은 전체 시연에 포함하기로 확정됐다 (8절 20번). 그래도 구조는 분리해 둔다.
- 따라서 관심사가 빠지든 들어가든 가입·로그인·로그아웃·탈퇴는 똑같이 동작해야 한다.

### 5.2 관심사를 독립 모듈로 둔다

| 계층 | 회원(기본) 파일 | 관심사 파일 (분리) |
|---|---|---|
| api | `api/auth.py`, `api/me.py` | `api/interests.py` (라우터 따로) |
| services | `services/auth_service.py` | `services/interest_service.py` |
| repositories | `repositories/user_repository.py`, `repositories/token_repository.py` | `repositories/interest_repository.py` |
| schemas | `schemas/auth.py`, `schemas/user.py` | `schemas/interest.py` |
| 마이그레이션 | 회원 테이블 리비전 1개 | 관심사 테이블 리비전 1개 (회원 리비전 다음에 붙음) |

> 파일 이름은 설계안이며 승인 후 확정한다.

- **users 테이블은 관심사에 의존하지 않는다.** 관계는 `user_interests.user_id → users.id` 한 방향뿐이다. 관심사 테이블이 없어도 users는 그대로 만들어진다.
- 탈퇴 시 관심사 삭제는 FK의 `ON DELETE CASCADE`로 처리해, 탈퇴 코드가 관심사 모듈을 부르지 않아도 된다.

### 5.3 기존 계약과 호환

- 가입 요청의 `interests` 필드는 **선택**이고 기본값은 빈 목록이다. 관심사 없이 이메일·비밀번호만 보내는 기본 가입 요청이 그대로 통한다.
- 관심사 라우터는 main에서 **한 줄로 등록**한다. 그 한 줄을 빼도 가입·로그인·로그아웃·탈퇴는 동작한다.
- 모든 경로는 `/v1` 접두사, 에러는 공통 형식 `{code, message, request_id}`를 쓴다. 회원 파트가 별도 형식을 만들지 않는다.

### 5.4 DB 마이그레이션 규칙

- 테이블 변경은 Alembic으로만 하고, **SQLite와 PostgreSQL에서 모두 통하는 공통 문법만** 쓴다 (로드맵 "두 DB의 동일 마이그레이션").
  - PostgreSQL 전용 타입(JSONB, 네이티브 ENUM 타입, 배열 등)은 쓰지 않는다. 관심사 코드·역할은 문자열 컬럼으로 저장하고 값 검증은 Pydantic Enum에서 한다.
  - 시각은 UTC로 저장한다.
  - SQLite는 컬럼 변경(ALTER)이 제한적이므로 Alembic의 batch 모드를 쓴다.
- 각 리비전은 `downgrade`를 작성해 되돌릴 수 있게 한다 (AGENTS.md 7절). 관심사를 빼야 하면 관심사 리비전 하나만 되돌리면 된다.
- 다른 팀원 리비전과 순서가 엉키지 않도록, 리비전을 만들기 전에 팀의 최신 head를 확인하고 그 뒤에 붙인다.
- `.db` 파일은 Git에 올리지 않는다. DB 위치는 환경변수 `DATABASE_URL`로 받는다.

### 5.5 그 밖의 합치기 규칙

- SQL은 `repositories/`에만 둔다. 다른 파트는 회원 테이블을 직접 조회하지 않고 서비스 함수로만 쓴다.
- 설정은 팀 공통 `BaseSettings` 하나를 쓰고, 새 환경변수는 이름만 `.env.example`에 추가한다.
- 테스트는 회원 파트 전용 폴더에 두고 sqlite 메모리 DB를 써서 네트워크 없이 돈다. 다른 파트 테스트와 DB를 공유하지 않는다.
- 공통 기반(앱 생성, 로깅, 에러 처리)을 회원 파트가 따로 만들지 않는다. 팀장·백엔드와 누가 만들지 먼저 정한다 (8절 3번).

머지 요청 전에 기능을 만들고, 아래 두 문서를 기준으로 실제 동작을 시험한다. 기능을 만들 때마다 지킨다.

- `08_단위_test_cases_v1.0.1.md` (이하 08): 무엇을 시험할지 (UT ID별 입력·기대결과)
- `09_단위_test_procedure_v1.0.1.md` (이하 09): 어떻게 실행하고 증거를 남길지

### 13.1 이해한 내용 요약

**공통 판정 규칙 (08 2절, 20절)**
- 모든 테스트는 독립 실행이 가능하고 실행 순서에 의존하지 않는다.
- 시간은 fake clock, ID는 고정 fixture를 쓴다.
- 실패 응답에 stack trace, 비밀번호, 토큰, 이메일 원문, 내부 SQL이 있으면 실패다.
- API 모델은 `extra="forbid"` 정책을 검증한다.
- 완료 기준: P0/P1 PASS, flaky 0, **외부 네트워크 호출 0**, 실제 LLM/SMTP 호출 0, 순서 의존 0, 실패 테스트를 skip/xfail로 숨기지 않음, 테스트 실패 시 ID로 어느 기능·API·DB 규칙이 깨졌는지 추적 가능.
- 공통 테스트 데이터: USER-A(`usr_test_a`/`usera@example.com`), USER-B(`usr_test_b`/`userb@example.com`).

**실행 환경과 절차 (09)**
- Windows 10/11, Python 3.12+, PowerShell. 가상환경 `py -3.12 -m venv .venv` 후 활성화.
- 테스트 DB는 SQLite 또는 격리된 임시 PostgreSQL schema. 실제 DB·Redis·SMTP·LLM 자격 증명 사용 금지. Redis·LLM·SMTP는 fake로 대체.
- 정적 검사(5절): `ruff check .` → `ruff format --check .` → `pyright`. 하나라도 실패하면 품질 게이트 실패로 기록.
- 단위 테스트(6절): `pytest tests/unit -q`, 상세 `-vv`, 조사 시 `-x -vv`.
- 인증 기능별 실행(7.1절): `pytest tests/unit/services/test_auth_service.py -vv`, `pytest tests/unit/api/test_auth_schemas.py -vv`.
- 실패 조사(10절): UT ID 확인 → 단일 재현(`-vv -s`) → 실제/기대 diff → mock 호출 횟수·인자 → DB 변경 전후 → 수정 후 해당 테스트 → 기능군 → 전체 회귀. 증거는 11절 양식(Test ID, Commit, 실행 명령, 입력, 기대, 실제, 관련 FR/API/DB, 원인, 수정, 재검증)으로 남긴다.
- 종료 조건(14절): 정적 검사 3개와 `pytest tests/unit -q`가 모두 성공, P0/P1 실패 0, 이유 없는 skip 0, flaky 0, 외부 네트워크 0, 로그 민감정보 0.
- 경계 검토(13절): 제약을 일부러 지웠다고 가정하고 테스트가 잡는지 점검한다 (예: user_id scope 제거, dedupe unique 제거).
- 권장 폴더: `tests/unit/{api,services,repositories,...}`, `tests/fixtures/`. 회원 테스트는 이 구조 아래에 두되 파일 이름으로 구분한다 (5.5절과 충돌 없음).

### 13.3 08에 없는 부분

- **관심사(6절)는 08의 테스트 케이스 요구에 없는 항목이다.** 회원 파트가 자체 판단으로 같은 규칙(독립 실행, 네트워크 0, 정상·경계·차단 사례)의 테스트 케이스를 만들어 진행하며, 08에 있는 것처럼 쓰지 않는다. 문서 반영 요청은 10.1절 5번.
- 08의 UT-AUTH-011은 설정·예약 정리를 말하지만 그 테이블은 다른 파트 몫이다. 회원 파트는 자기 테이블(refresh_tokens, user_interests)을 지우고, 나머지는 인터페이스로 지울 수 있게 비워 둔다. 합칠 때 확인한다.

### 13.4 테스트 완료 표기 규칙

- 12절 기능 기록의 "테스트 결과"에는 **실제로 실행했을 때만** 다음 문장을 쓴다.
  "해당 기능은 08 단위 test cases 파일과 09 단위 test procedure 파일을 기준으로 테스트가 완료되었습니다."
- 문장 뒤에 실제 명령 출력과 통과/실패 수를 붙인다. 실행하지 못했거나 일부만 했으면 문장을 쓰지 않고 그대로 적는다.
- 구현은 AGENTS.md·CLAUDE.md를 따른다. 08·09와 어긋나는 점은 8절에 적고 사용자에게 보고한다. 08·09는 구현 후 자체 테스트 기준이다.
