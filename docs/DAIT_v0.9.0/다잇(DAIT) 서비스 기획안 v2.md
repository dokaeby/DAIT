# 다잇(DAIT) 서비스 기획안 v2

AI 트렌드 큐레이션 웹 대시보드 · 5인 팀 · 2주 MVP

> 초안의 범위 통제와 환각 대응 설계는 유지하고, 완료 기준 수치화, 출처 조기 확정, 데이터 스키마 선합의, 백업 담당 지정, 비용·배포 기본안을 보강한 버전입니다. 표시한 "기본안"은 첫 회의에서 팀이 확정하거나 바꾸는 제안값입니다.

## 1. 서비스 한눈에 보기

**정의**: 다잇은 AI 소식을 한국어로 요약하고, 주니어 웹 개발자와 AI에 관심 있는 비개발자가 각자의 관점에서 이해하도록 돕는 웹 대시보드입니다.

**한 줄 가치**: 하나의 소식을 *핵심 요약 · 개발자 관점 · 쉬운 설명* 세 가지로 보여주고, 원문 링크로 직접 확인하게 합니다.

**이번 프로젝트의 목표**

- 지정 출처 1곳에서 소식을 수집하고 AI로 요약해 웹에 표시한다.
- 키워드로 저장된 소식을 검색하고 원문으로 이동할 수 있다.
- 수집부터 검색까지의 흐름과 요약 품질을 숫자 기준으로 검증하고 기록한다.

## 2. 문제와 사용자

**문제**

- 정보 탐색: AI 소식이 여러 출처에 흩어져 있어 찾아 읽는 데 시간이 든다.
- 이해의 장벽: 영문 자료와 전문 용어 때문에 배경지식이 적은 사람은 핵심을 파악하기 어렵다.
- 실무 연결: 개발자는 새 발표가 자기 작업에 어떤 의미인지 빠르게 판단할 단서가 필요하다.

**대상 사용자**

- 주니어 웹 개발자: AI 기능을 공부하거나 개발하며 새 도구와 발표의 실무 관련성을 알고 싶은 사람
- AI에 관심 있는 비개발자: 전문 용어와 영문 자료가 부담스럽지만 변화의 의미는 알고 싶은 사람

회원 구분 없이 모든 사용자에게 같은 콘텐츠를 제공합니다.

## 3. MVP 범위

**포함 (2주 안에 반드시)**

1. 지정 출처 1곳에서 새 글 수집 (제목, 링크, 날짜, 요약 가능한 내용)
2. 링크 또는 고유 ID 기준 중복 확인
3. AI 요약 3종 생성 (핵심 요약, 개발자에게, 쉽게 말하면)
4. 결과 검토 상태 표시 (정상 / 검토 필요 / 실패)
5. 목록 화면 + 상세(또는 펼치기) 화면, 원문 링크
6. 제목·핵심 요약 키워드 검색 (검색어 없음, 결과 없음 처리 포함)
7. 수집·AI 실패 안내와 재시도

**제외 (향후 확장)**

자연어 지시 탐색, 예약 수집, 회원가입·계정 연결, 개인화 추천, 인기 랭킹, 디스코드 자동 발송, 멀티 에이전트 구조

**"자동 수집"의 정의**: 버튼 클릭 또는 스크립트 실행 **한 번**으로 수집 → 중복 확인 → AI 요약 → 저장까지 사람 손 없이 이어지는 것을 말합니다. 정해진 시간에 저절로 도는 예약 수집은 범위 밖입니다.

## 4. 완료 기준 (합격선)

발표에서 "됐다"를 숫자로 말할 수 있도록 아래 기준을 사용합니다. 수치는 기본안이며 첫 회의에서 조정합니다.

- **수집 흐름**: 실행 1회로 수집 → 요약 → 저장 완료, 최소 10건 확보
- **중복 방지**: 같은 출처를 2번 연속 실행해도 중복 저장 0건
- **출력 형식**: 검토 대상 10건 중 필수 항목 3종(핵심 요약·개발자에게·쉽게 말하면) 누락은 "검토 필요"로 분류되고, 정상 표시된 건의 누락은 0건
- **사실 정확성**: 팀원 2인이 교차로 대조한 10건 중 원문에 없는 사실이 포함된 건 1건 이하 (발견 시 수정하고 기록)
- **검색**: 일치 / 미일치 / 빈 검색어 3가지 모두 기대대로 동작
- **실패 처리**: 수집 실패와 AI 요청 실패 시 안내 문구 표시, 재시도 가능
- **화면**: 데스크톱과 모바일(폭 360px 기준)에서 목록·검색·상세가 깨지지 않음
- **시연**: 실시간 시연 + 사전 검토 결과 백업을 모두 준비

## 5. 사용 흐름과 기능 명세

**핵심 흐름**: 수집 실행 → 출처에서 가져오기 → 중복 확인 → AI 요약 → 형식 점검 → 저장 → 웹 표시 → 키워드 검색 → 원문 링크 열기

- **수집**: 선정 출처 1곳에서 제목, 링크, 날짜, 요약 가능한 내용을 가져옵니다. 실패·중복·내용 부족은 기록하고 재실행할 수 있어야 합니다.
- **AI 요약**: 원문에 근거한 한국어 결과 3종을 만듭니다. 핵심 요약은 원문에 나온 변화만, 개발자에게는 개발 시 확인할 점, 쉽게 말하면은 배경지식 없이 이해되는 설명입니다.
- **사실과 해석의 구분**: 개발자 영향은 AI의 해석일 수 있습니다. 화면에 "AI 해석" 표시를 붙이고, 근거가 부족하면 추측하지 않고 "추가 확인 필요"로 표시합니다.
- **검토**: 팀원이 생성 결과를 원문과 비교합니다. 공개 전 검토를 권장하되 별도 승인 화면은 만들지 않고, 상태값(정상 / 검토 필요)으로만 구분합니다.
- **대시보드**: 제목, 출처, 날짜, 요약 결과, 상태 표시. 펼치기와 상세 화면 중 구현이 쉬운 쪽을 고릅니다.
- **검색**: 제목과 핵심 요약에서 키워드를 찾습니다. 검색어가 없으면 전체, 결과가 없으면 안내를 보여줍니다.

## 6. 데이터 스키마 (1주 차 초반 합의 필수)

수집, AI, 화면 담당이 같은 형식을 쓰도록 첫 주 초반에 아래 구조를 확정하고, 가짜(mock) 데이터로 화면 개발을 바로 시작합니다.

```json
{
  "id": "출처 고유 ID 또는 링크 해시",
  "source": "출처 이름",
  "title": "원문 제목",
  "url": "원문 링크",
  "publishedAt": "2026-11-05T09:00:00+09:00",
  "collectedAt": "수집 시각",
  "rawExcerpt": "요약에 쓴 원문 내용(내부용, 화면 비노출)",
  "summary": {
    "core": "핵심 요약",
    "forDevs": "개발자에게",
    "plain": "쉽게 말하면",
    "needsCheck": ["근거가 부족해 추가 확인이 필요한 항목"]
  },
  "status": "ok | needs_review | failed",
  "error": "실패 사유(없으면 null)"
}
```

## 7. 출처 선정 기준과 Plan B

출처는 프로젝트 전체 일정을 좌우하는 가장 큰 변수이므로 **킥오프 첫날**에 결정합니다.

**절차**: 후보 2\~3곳을 정하고 아래 체크리스트로 바로 확인합니다. 통과한 곳 중 1곳이 주 출처, 1곳이 Plan B입니다.

- RSS/Atom 또는 공식 API를 제공하는가
- 이용 약관이 수집과 요약 표시를 허용하는가
- 피드가 본문을 얼마나 주는가 (일부만 주면 요약 품질이 떨어질 수 있음)
- 최근 2주 게시량이 10건 이상인가
- 한국어 요약 품질을 시험할 만한 분량과 난이도인가

**저작권·이용 원칙**: 원문 전문은 저장·표시하지 않습니다. 화면에는 제목, 출처, 날짜, 직접 작성된 요약과 원문 링크만 보여줍니다. 요약에 쓴 원문 일부는 내부 처리용으로만 두고 화면에 노출하지 않습니다.

**Plan B 전환 조건**: 첫날 확인에서 접근 불가이거나, 이틀 안에 수집 프로토타입이 동작하지 않으면 Plan B로 전환합니다.

## 8. AI 요약 설계

- **프롬프트 원칙**: 제공된 원문 내용에 있는 사실만 요약하고, 없는 내용은 만들지 않으며, 개발자 영향은 근거가 있을 때만 쓰고 없으면 `needsCheck`에 남깁니다.
- **출력 형식**: 위 스키마의 `summary` 구조(JSON)로 받습니다. 파싱 실패나 필수 항목 누락은 `needs_review`로 저장합니다.
- **실패 처리**: 요청 실패나 지연 시 타임아웃 후 재시도하고, 반복 실패하면 `failed`로 기록해 화면에 안내합니다.
- **키 관리**: API 키는 서버(환경 변수)에서만 관리하고 화면 코드나 저장소에 넣지 않습니다.
- **비용 기본안**: 1회 실행당 요약 최대 15건, 건당 재시도 최대 2회, 타임아웃 30초. 팀이 쓸 AI 서비스와 요금을 확인한 뒤 상한을 조정합니다.
- **한계 인식**: 형식 검사는 사실 검증을 보장하지 않으므로 사람의 원문 대조가 필수입니다.

## 9. 기술 구성 기본안

팀 경험에 따라 바꿀 수 있는 제안입니다. 원칙은 "가장 익숙한 도구로 가장 단순하게"입니다.

- **구성**: 수집 스크립트 → 서버(중복 확인, AI 호출) → 저장소 → 웹 화면(목록, 검색, 상세)
- **저장소**: 파일(JSON) 또는 가벼운 DB 중 팀이 익숙한 것. 10\~수십 건 규모라 복잡한 구성은 필요 없습니다.
- **검색**: 제목과 핵심 요약에 대한 단순 문자열 포함 검색으로 시작합니다.
- **배포**: 기본안은 **로컬 시연**입니다. 배포는 일정에 여유가 생길 때만 선택 과제로 둡니다.
- **반응형**: 화면 담당자는 처음부터 모바일 폭을 고려해 만듭니다.

## 10. 품질·테스트 계획

- **누적 기록**: 테스트 기록은 마지막 주에 몰아 쓰지 않고 1주 차부터 기능이 생길 때마다 쌓습니다. 항목은 *확인 항목, 확인 방법, 기대 결과, 실제 결과, 수정 여부*입니다.
- **원문 대조**: 서로 다른 원문 10건에 대해 작성자가 아닌 다른 팀원이 원문과 대조합니다. 원문에 없는 사실, 과장, 근거 없는 개발자 영향을 표시하고 프롬프트를 수정한 뒤 다시 확인합니다.
- **시나리오 점검**
  - 실제 출처 수집, 연속 2회 실행 시 중복 방지
  - 3종 요약 생성과 필수 항목 누락 처리
  - 검색 일치 / 미일치 / 빈 검색어
  - 수집 실패, AI 요청 실패, 요약할 내용 부족
  - 원문 링크 이동, 목록 및 모바일 화면
- **발표용 결과**: 원문과 대조를 마친 건만 발표에 사용합니다.

## 11. 역할 분담 (주담당 / 백업)

한 사람이 막혀도 일정이 멈추지 않도록 모든 영역에 백업을 둡니다. 기본 제안이며 팀원의 기술 경험을 보고 확정합니다.

- **기술 리드 (백업: 데이터·연동)**: 최소 구조와 연결 방식 결정, 통합, 코드 리뷰. 리뷰가 몰리지 않도록 작은 단위로 자주 합칩니다.
- **AI 처리 (백업: 기술 리드)**: 요약 요청, 프롬프트, 결과 형식, 실패·재시도 처리
- **웹 화면 (백업: 기획·검증)**: 목록, 검색, 상세, 오류 안내, 반응형
- **데이터·연동 (백업: AI 처리)**: 출처 수집, 중복 확인, 저장·표시 연결
- **기획·검증 (백업: 웹 화면)**: 사용자 흐름, 테스트 기록, 원문 대조 관리, 발표 준비

최종 검토와 원문 대조는 전원이 참여합니다. 통합 주간에는 영역 간 2인 페어 작업을 권장합니다.

## 12. 2주 일정 (일 단위 제안)

수업 시간(평일 09:00\~18:00)을 고려해 작업은 저녁과 주말 중심으로 가정합니다. 실제 가용 시간을 확인한 뒤 일정과 범위를 조정합니다.

**1주 차: 기반 확정과 병렬 개발**

- 1일: 킥오프, 역할·백업 확정, 출처 후보 점검 및 주 출처 + Plan B 결정, 완료 기준 확정
- 2일: 데이터 스키마(JSON) 합의, 저장소·기술 스택 확정, AI 서비스 접근과 비용 상한 확인
- 3\~4일: 병렬 개발 (수집 프로토타입 / 프롬프트 + 요약 호출 / mock 데이터 기반 목록·검색 화면). 이틀 내 수집이 안 되면 Plan B 전환
- 5일: 중간 점검. 각 부분이 스키마대로 입출력하는지 확인, 테스트 기록 시작
- 주말: 버퍼 (밀린 작업, 수집 결과로 프롬프트 1차 보정)

**2주 차: 통합, 검증, 시연**

- 6일: 수집 → 요약 → 저장 연결, mock 데이터를 실제 데이터로 교체
- 7일: 연결 완료 후 검색·상세·오류 안내 점검, 중복 방지 확인. 실행 1회 end-to-end 성공이 목표
- 8일: 원문 대조 1차 (10건), 프롬프트 수정, 모바일 화면 점검
- 9일: 실패 시나리오 테스트(수집 실패, AI 실패, 내용 부족), 재시도 확인, 기능 동결
- 10일: 최종 원문 대조, 테스트 결과 정리, 시연 리허설, 사전 검토 결과 백업 준비
- 발표일: 시연 + 테스트 결과 공유

**범위 조정 규칙**: 7일 차까지 end-to-end가 연결되지 않으면 상세 화면 등 부가 기능부터 줄이고, 완료 기준의 핵심(수집 → 요약 → 검색 → 원문 링크)을 지킵니다.

## 13. 리스크와 대응

- **출처 접근 불가·약관 문제**: 첫날 점검 + Plan B, 전환 조건 사전 합의
- **피드가 본문을 일부만 제공**: 요약 가능 범위를 첫날 확인하고, 내용 부족은 "검토 필요"로 처리
- **AI 환각·과장**: 원문 근거 한정 프롬프트, 사실/해석 구분 표시, 교차 원문 대조
- **AI 호출 실패·지연·비용 초과**: 타임아웃, 재시도 상한, 건수 상한, 사전 검토 결과 백업
- **통합 지연**: 스키마 선합의, mock 데이터 선개발, 5일 차 중간 점검
- **특정 인원 병목·결원**: 영역별 백업, 작은 단위 리뷰와 잦은 병합
- **테스트 기록 몰림**: 1주 차부터 누적 기록

## 14. 시연 계획

1. 수집 실행 한 번으로 새 소식이 저장되고 요약이 생성되는 과정 시연
2. 목록에서 3종 요약과 "AI 해석" 표시, 상태값 확인
3. 키워드 검색 (일치, 미일치, 빈 검색어)
4. 원문 링크로 이동해 요약과 원문 대조
5. 실패 상황(수집 또는 AI 실패) 안내와 재시도
6. 테스트 결과 수치 공유 (완료 기준 대비)

호출이 어려운 상황을 대비해 사전 검토한 결과를 준비하고, 시연 중 어떤 부분이 실시간이고 어떤 부분이 사전 결과인지 밝힙니다.
